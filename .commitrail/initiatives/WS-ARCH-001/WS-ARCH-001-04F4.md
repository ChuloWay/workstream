# ARCH-04F4 — Operator recovery of terminal checker infrastructure failure

- Initiative: `WS-ARCH-001`
- Durable disposition: `Complete`
- Intended merge outcome: an exact, reason-bound Operator request can reserve and dispatch one new CHECKERS generation after the current run has terminal `infrastructure_failed` evidence, while the failed run remains immutable.

## Intent

The first contributor journey must recover when the platform cannot finish a post-submit check. Today an expired unfinished lease is reclaimed on the same run, but `PostSubmissionExecutor` replays a terminal `infrastructure_failed` result without executing again. `EvaluationCoordinator` already owns the per-Submission generation/fence transaction. Initial `SubmissionDispatch` and `EvaluationRequestHandler` carry only generation one; `operations.checker.retry` is an Operator permission with a planned, unavailable action. No public recovery command exists. `task_setup_blocked` is a different completed result: CHECKERS shows its details only in management history, TASK does not route it to contributor remediation, and this change does not treat it as infrastructure failure.

This is one hidden recovery command and its exact delivery through the existing worker, not a second checker runner, retry job subsystem, or public API. The next separate boundary is an authorized manager-visible setup-fault hold: retain the Submission and locked rules without contributor penalty. Changing or re-screening a submitted task under different rules is deferred.

### Design and decisions

The hidden command takes the Operator's request key, reason, and exact source run. Detached, nonlocking lookup may select owner IDs before the transaction locks, but cannot choose a durable new/replay branch. Both paths lock the exact source TASK → Assignment → historical Submission and reread the actor/key receipt while holding TASK custody. A receipt takes the historical replay path even if task and assignment subsequently completed or the Submission ceased to be latest. Only an absent receipt then takes the stricter latest submitted Submission, active Assignment and `evaluation_pending` guard for a new request. Both paths then lock AUTH control → actor/link → active system Operator grant, and only then take CHECKERS custody: the per-Submission advisory key → fence → source/current run for a new request, or the retained receipt/source/successor closure for replay. The active grant remains locked through consumption and the atomic successor/receipt/event commit. No AUTH lock or decision is taken while waiting for TASK. The same Operator's existing TASK start-override command uses TASK-before-AUTH; reversing this order would form a real cycle. Missing, foreign and changed owner facts deny under this sequence before byte I/O.

New-request eligibility is rechecked after all locks: the selected source must be the exact current `infrastructure_failed` run, with complete immutable result/finalization evidence, no newer Submission or routed outcome, and task `evaluation_pending`. `TaskEvaluationGuard.lock_terminal_retry_scope` supplies the first TASK locks, exact Submission lineage and active assignment/status check; its existing `lock_evaluation_scope` remains unchanged for ordinary generation/current reads. The new request copies the stored bounded content and locked lineage; only request ID, digest and generation change. The retry command enters the coordinator's factored CHECKERS reservation body after its TASK guard and fresh AUTH locks, without invoking the public `reserve_current_evaluation` method after AUTH; the public method still performs its ordinary TASK lock first. The coordinator reserves the successor and advances the fence in the caller transaction. Prepared AUTH binds actor/link, action/permission, system-only scope, source terminal tuple, reason and key at preparation; its final resource binds the actual coordinator-returned successor request/run/result IDs, supersession, fence, audit and exact request event. One durable CHECKERS retry receipt closes those values and the actual AUTH decision in the same commit. The SQL closure verifies their identity, not just caller-selected values.

Replay selects the retained actor/key receipt and owner-qualifies its exact historical TASK/Assignment/Submission first, then prepares fresh Operator authority and uses an action-specific validator for the original AUTH event/resource digest and complete committed receipt/event/run closure. The replay TASK guard verifies retained owner and locked-lineage identity without requiring `evaluation_pending`, an active assignment, latest Submission, or current source/fence; successful routing and auto-accept may already have changed all four. Replay never advances the fence or appends another run or request event. A different key for an already-owned source conflicts. The existing request handler selects the initial `SubmissionDispatch` only for generation one and the retry receipt only for later generations. Exactly one committed source must match the complete v1 event payload; neither payload nor missing-source fallback supplies authority. The handler invokes the same executor and keeps production registration disabled.

The current generic coordinator permits later generations for its own currentness/race consumers. This change does not silently narrow it: the Operator command enforces terminal eligibility, while deferred SQL requires a matching authorized retry receipt whenever a fence supersedes an `infrastructure_failed` run. The receipt/SQL closure proves that trigger's authority at commit without changing valid queued/completed-success successor controls. A separate source-unique constraint ensures one retry per failed run even under different keys. A valid queued or completed-success generation-two control must still commit. If another reachable path requires terminal-failure supersession, revise this record with a discriminating control instead of adding a bypass.
