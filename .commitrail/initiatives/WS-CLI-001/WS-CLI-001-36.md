# WS-CLI-001-36 — Inspect Operator tasks and explicitly override start

- Initiative: `WS-CLI-001`
- Durable disposition: `Complete`
- Intended merge outcome: A system Operator can inspect the existing status-only task queue and exact locked policy references, then deliberately invoke the existing reasoned start override through the public API.

## Intent

Close issue #609's three-operation CLI gap without giving the terminal client lifecycle authority. This matters when an Operator must identify a task, inspect its locked lineage, and explicitly start an existing assignment after the backend independently rechecks current authority. Reads are observations, not permission for a later write.

## Current behavior

`backend/app/modules/tasks/queue_router.py::operational_tasks` exposes a bounded status-only project page. `router.py::get_operational_task_locked_context` exposes exact-project policy references, and `router.py::override_task_start` requires `TaskTransitionRequest` and an `Idempotency-Key`. `authorized_commands.py::start` requires a nonblank override reason, retains the assignment, and uses a distinct `operations.task.start_override` decision and replay. `cli/internal/command/command.go` currently registers contributor `task start` but no Operator task command. Issue #608 separately introduces the `operations` Cobra root for checker operations; its branch is not the base of this change.

## Design and decisions

Add `operations task list PROJECT_ID [--limit N] [--cursor TOKEN]`, `operations task locked-context PROJECT_ID TASK_ID`, and `operations task start TASK_ID --reason TEXT --idempotency-key UUID`. The root owns one explicit Operator namespace, with task registration accepting that root so #608's checker group can be joined at reconciliation. The list decoder accepts only the server's five-field operational summary, binds every item and page to the requested project, checks status/time/duplicate IDs, and treats the cursor as opaque. The context decoder binds both selectors and validates every required immutable lineage UUID, digest, positive generation and nonblank version, without fetching or interpreting policy bodies. Start sends one POST only to the override route with the exact reason/key; it validates the returned `in_progress` contributor-safe `TaskResponse` and treats malformed or ambiguous success as outcome unknown. Manual replay must reuse the unchanged task, reason and key. No contributor-start fallback, local grant check, or inferred assignment identity is introduced: the override response deliberately omits `assigned_to` and the assignment remains backend-owned.

Alternatives rejected: putting override under contributor `task start` would obscure the separate authority; treating management detail as Operator context would widen disclosure; stacking #608's implementation would mix ownership and complicate review.
