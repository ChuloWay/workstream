# WS-CLI-001-46 — System-covered project catalogue

- Initiative: `WS-CLI-001`
- Durable disposition: `Complete`
- Issue: [#663](https://github.com/Flow-Research/workstream/issues/663)
- Intended merge outcome: A minimal public project catalogue and explicit CLI page read let holders of a current system-wide Project Manager, Operator, Finance Authority, or Audit Authority grant find projects by name without treating exact-project membership as global discovery.

## Intent and current boundary

`GET /api/v1/actors/me/projects` currently lists only active exact-project grants. `actor.project.list` is an actor-self action; a system grant adds effective roles to listed rows but enumerates no projects (`docs/spec_authorization_service.md`). The separate exact-project `project.read` action permits a system-wide Project Manager, Operator, Finance Authority, or Audit Authority to inspect a known project. Access Administrator has no `project.read` permission. Requiring a UUID obtained out of band makes the intended administrative terminal picker unusable. The human decision for this chunk is to permit those four existing system-wide project-reader roles, but no others, to enumerate only project ID, name and status.

## Bounded change and plan

1. Add one `project.catalogue.list` AUTH action mapped to existing `project.read`, with an exact actor-owned collection context, a fresh active-human/system-scope-only grant check restricted to the four named roles, grant locking through the canonical AUTH repository, and decision/audit provenance. Extend the existing closed audit action/permission CHECK with that exact pair in one narrow migration; it otherwise rejects even denied decision evidence. Deny services, Access Administrator alone, exact-project-only grants and contributor-only grants. Do not modify `actor.project.list`.
2. Extend the PROJECTS-owned summary reader/public port with a separate bounded project-ID keyset page over all projects containing only ID, name and status. ID order is stable enumeration, not creation, commit or business order. Do not materialize every project ID or join guide, task, source, actor or payment rows. Use the existing snapshot-read and signed cursor conventions to bind actor, action, query and limit; the cursor position discloses only the already-public ID. Authorize before cursor parsing on every page. New `GET /api/v1/projects` returns only that page and an opaque `next_cursor`.
3. Add `workstream project list [--limit N] [--cursor TOKEN]`, using the existing typed public client and stable text/`--output json`/structured error conventions. No TUI runtime is part of this PR. Update the canonical authorization spec, CLI README and affected roadmap/initiative navigation for the intended merged outcome.

## Acceptance and proof

- Each of the four named *system-scoped* roles independently obtains pages of only project ID, name and `draft|active|paused|archived` status, including a project lacking an exact grant. Same-project overlaps do not duplicate rows; page size is 1–100 with stable ID order and a bounded response. The cursor envelope must not expose creation timestamps or any other undisclosed project fact.
- A system Access Administrator alone, exact-project Project Manager/Finance/Audit, Submitter/Reviewer and unrelated actor cannot enumerate; an existing exact project grant remains visible only through unchanged `me projects`. Absent/denied cases never reveal private project facts or substitute an empty success.
- Every page starts from current actor and system grant authority; cursor tampering, cross-actor/limit/action reuse is refused, and revocation committed before a later page removes catalogue access. A concurrent revoke cannot commit until an already-authorized response releases its locked grant; an in-flight response may still arrive after that later commit. AUTH decision and evidence identify the matched system grant.
- The PROJECTS read uses one bounded SQL page of three columns in primary-key order, not a full project-ID set. Demonstrate real PostgreSQL storage and actor/resource isolation, grant revocation/concurrent-session locking, and no duplicate/gap pagination. The primary-key keyset avoids a catalogue-wide sort; production-scale latency is unmeasured and not claimed. A projection/response validation failure must roll back its AUTH decision evidence. The new audit CHECK must accept the exact pair and reject a crossed pair by direct SQL while retaining the valid row.
- CLI text escapes untrusted terminal controls, JSON preserves validated public values, failures retain stable bounded structured stderr and no partial stdout. Existing `workstream me projects`, `project show/access`, and agent CLI output remain unchanged.
- Run focused backend/CLI tests, applicable full suites and public API drill, stale-wording scan, Markdown-link check, roadmap/INDEX reconciliation, and reviewer tracks on a clean candidate. Hosted backend lanes must select both new modules, and the separate CLI public-API lane must supply the built binary for the native drill; no test may silently skip when that binary is absent.

## Alternatives and remaining risks

Extending `me projects` with a system mode was rejected: exact-grant membership and system-wide catalogue selection have different permission/audit and disclosure contracts; reusing its `active_guide` field would over-disclose to system Finance. `GET /api/v1/projects` is the natural separate read on the existing PROJECTS owner and does not establish a second resolver. Client-side UUID entry remains available but does not solve discovery. A future TUI consumes the public read; it is not delivered here.

Potential risks are grant/actor race handling, cursor substitution, row projection drift, and unmeasured production-scale catalogue latency. The project-ID primary key supplies the page order without an added index; no delivery-time performance guarantee is claimed. The policy decision is resolved by the user; the human merge decision remains separate.
