# WS-CLI-001-20 — Explicit contributor role decisions

- Initiative: `WS-CLI-001`
- Durable disposition: `Complete`
- Intended merge outcome: Managers explicitly issue and revoke exact-project Submitter/Reviewer grants through the existing public AUTH APIs.

## Intent

CLI19 prepares ready work. Contributors still need an authorized project role
before claiming it. Add the two existing public mutation operations, not another
authorization or eligibility system:

```sh
workstream project role-grant issue PROJECT_ID --input FILE --idempotency-key UUID
workstream project role-grant revoke PROJECT_ID GRANT_ID --input FILE --idempotency-key UUID
```

Issue input is the exact closed `ProjectRoleGrantIssueBody`: target actor, one
of `submitter`/`reviewer`, explicit qualification evidence and reason. Revoke
input is the exact reason body. The CLI forwards the original bounded JSON;
never invent unavailable qualifications, trim a decision reason, discover
actors, grant automatically after task release, or infer manager authority.
The human or calling agent supplies the decision and evidence.

Each invocation sends one public POST and caller key. AUTH owns current actor
and identity-link admission, exact-project manager authority, eligible targets,
qualification capture, independent role grants, atomic audit and replay. A
Reviewer grant alone does not authorize task claim/start, and does not activate
the deferred human-review workflow. Project Manager is an AdminRole, not a third
contributor role. No adjudicator role is added.

Validate the entire seven-field mutation receipt: grant, qualification snapshot,
project and actor UUIDs, exact role, status and version. Issue must bind project,
target actor and role and return active/version 1. Revoke must bind project and
grant and return revoked/version 2; its actor/role are server-owned observations,
not client-inferred values from a prior read. Credential reflection or a
malformed/substituted success is an unknown write outcome with empty stdout.
Manual recovery uses exactly the same selectors, input and key. Replay still
requires current backend authority and matching retained grant state; an old
issuance key does not become valid again after its grant is revoked.

## Bounded change

Allowed: new `cli/internal/api/project_role_mutations.go`, new
`cli/internal/command/project_role_mutations.go`, command registration in
`cli/internal/command/command.go`; new
`cli/tests/integration/test_project_role_mutations.py` and small
`project_role_journey.py` helper called from retained
`contributor_task_journey.py`; README, CLI README, affected roadmap claims,
this record, initiative overview and index.

Reuse `readJSONInput`, closed/null-aware decoders, UUID identity comparison,
`requestWithKey` non-replaying transport, decoded credential safety, failure
envelopes and escaped text output. Keep existing contributor tests/assertions
and owner interfaces intact.

Prohibited: backend, AUTH decisions, grants/policies/schema/migrations,
dependencies or workflows; qualification discovery/scoring, eligibility,
automatic grants/revocation, role caches, access-administrator bootstrap commands,
Finance grants, hidden submission, grant browsing, unit-test suites or new gates.
Backend scope/qualification rules remain authoritative. Basic wire validation
does not grant authority or evaluate whether qualifications are sufficient.

Rejected: a generic admin mutation framework, a create/release/grant shortcut,
and copying backend authorization into the client. One typed receipt and two
explicit public operations suffice.

## Acceptance criteria

- Exact public path, unchanged JSON, bearer/key and 201 issue/200 revoke; one
  POST only, including HTTP/2 transport uncertainty. Original supported UUID
  selector spellings remain on the wire; comparisons use UUID identity.
- Invalid selectors/keys, oversized JSON, duplicate/unknown keys, missing/null
  required structures, invalid role/field types and malformed UUID arrays fail
  before HTTP. Qualification fields follow the public schema; absent and null
  unavailable reasons are not silently defaulted. Business denial remains AUTH's
  decision, not another client policy engine.
- Valid control precedes otherwise-valid foreign project/actor/grant/role,
  mismatched status/version, missing/null/unknown fields and malformed identity
  receipt cases. Exactly seven authorized fields are retained in JSON/text;
  terminal/credential safety and canonical denial versus unknown outcome hold.
- Reuse the retained public-socket/Flow/PREP/PostgreSQL journey. Replace one
  existing real Submitter issuance and its later revocation with CLI operations,
  preserve ensuing claim/start and revocation-denial assertions, and exercise a
  real Reviewer issuance without allowing Reviewer-only claim/start.
- Real proof compares retained grant/qualification and audit facts with the
  CLI receipt; immediate unchanged replay equals the receipt, changed body/key
  fails, issue replay after revoke refuses changed state. Arrange a separate
  exact-project manager grant through public setup for stored-foreign-project,
  contributor-only and suspension/revocation denial controls, with no forbidden
  grant effect. Current native prerequisite ordering matters: CLI19 revokes its
  scoped manager grant, so restore a covering grant before positive role writes.
  Give the helper's separate control actor AccessAdministrator authority through
  the public setup route: piling these independent lifecycle controls onto the
  retained bootstrap administrator exceeded its real 30/minute allowance in
  hosted proof. Preserve the limiter, counters and one-request behavior; do not
  disable limits or retry fixture writes to hide it.
- An independent scratch mutant removing only project-receipt binding must make
  the named hostile-response assertion fail after its valid control. Runtime
  proof uses real stored foreign resources, not nonexistent IDs or permissive
  authorization fakes. Shared upstream guide fixtures are not live inference or
  deployed Flow certification; unchanged concurrency proof stays hosted.
