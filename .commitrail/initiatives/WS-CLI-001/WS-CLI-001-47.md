# WS-CLI-001-47 — Reject release environments with administrator approval bypass

- Initiative: WS-CLI-001
- Durable disposition: Complete
- Intended merge outcome: The existing CLI release-control guard refuses an environment unless GitHub explicitly reports administrator protection-rule bypass disabled; no release is published by this change.

## Intent

The first CLI publication must wait for an independent human approval. GitHub permits administrators to bypass environment protection rules by default, but the merged guard checks required reviewers and self-review prevention without checking that bypass setting. A configuration that defeats the approval gate can therefore pass the source guard. This is a bounded fail-closed repair to issue #562, not a new release channel or permission model.

## Current behavior

`scripts/check_cli_release_controls.py::validate_environment` checks the `cli-release` name, a required-reviewer rule with `prevent_self_review`, and the sole `main` deployment branch policy. `scripts/test_cli_release_controls.py` has no administrator-bypass case. A valid-looking environment with `can_admins_bypass: true` currently passes validation. The `release_guard` and `publish` jobs both call this validator with the environment returned by GitHub's GET endpoint. GitHub's documented GET endpoint accepts Actions read permission; the repository's existing public environment response exposes `can_admins_bypass: false`, including without authentication. Missing or altered fields in a future response must fail closed.

## Bounded change

### Allowed

- `scripts/check_cli_release_controls.py`: require the existing environment response to contain literal `can_admins_bypass: false`.
- `scripts/test_cli_release_controls.py`: preserve existing controls and add a discriminating pass/fail matrix for administrator bypass and unknown field values.
- `docs/engineering/cli-release.md`: tell the release administrator to disable the GitHub UI bypass option and verify the GET response before approval.
- This change record: intent, proof and remaining human boundary.

### Not allowed

No workflow, permissions, package, CLI, backend/API, roadmap, overview or index change; no GitHub setting, environment, tag, release, dispatch, secret or credential write. Do not infer a false bypass value from an omitted field or add an undocumented API write parameter. Do not contact the named independent approver; the product owner coordinates that approval.

## Design and decisions

Extend the existing `validate_environment` owner with an identity check (`is False`) before the other environment-policy checks. A missing key, null, true or string value is not proof that administrator bypass is disabled. The existing `github_json` path and job permission split stay unchanged. GitHub's documented environment PUT parameters do not include this setting; the operator runbook uses the documented UI control and a read-only GET verification. A separate manual-only check was rejected because it leaves the machine guard able to pass a bypass-enabled environment. No parallel control service or token is needed.

## Acceptance criteria

- [x] An environment with literal `can_admins_bypass: false` and the existing valid reviewer/branch controls passes; all existing tag-ruleset checks remain unchanged.
- [x] `true`, `null`, a missing field, string values and numeric `0` each fail before native release builds or publication; the regression fails against the merged pre-fix guard.
- [x] The operator instructions identify the UI setting and read-only verification without claiming the workflow can configure it.
- [x] Existing workflow permissions, native proof, archive assembly and public-release status remain unchanged. The absent live `cli-release` environment still blocks release preparation; no tag or release is created.
