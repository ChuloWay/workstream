# WS-CLI-001-23 — Manage contribution-policy drafts and publication

- Initiative: `WS-CLI-001`
- Durable disposition: `Complete`
- Intended merge outcome: explicit Finance draft creation, rule replacement,
  publication and retirement through the existing public REST operations.

## Intent

Extend the existing `project contribution-policy` group with `create PROJECT_ID`,
`update PROJECT_ID POLICY_ID VERSION_ID`, `publish PROJECT_ID POLICY_ID VERSION_ID`
and `retire PROJECT_ID POLICY_ID VERSION_ID`. Create/update take an input JSON
file; every command requires a caller-owned UUID idempotency key. Publish/retire
send the closed empty decision. Each invocation sends one mutation, with no
preflight discovery, automatic publication or transport/application retry.

## Bounded change

Allowed: new API/command `contribution_policy_mutations.go`, registration in
`contribution_policy_reads.go`, new process test
`cli/tests/integration/test_contribution_policy_mutations.py`, existing

the existing HTTP fixture's PUT handler using its shared request recorder;
the shared client transport's PUT mutation classification, replay refusal and
canonical-error handling (the first JSON PUT exposed a POST/PATCH-only branch);
README, CLI README, affected roadmap sections, initiative overview/index and
this record. Existing shared CLI helpers may be reused, not duplicated.

Prohibited: backend changes, schema/migrations, authorization or economic rules,
adapter bindings, dependencies, CI configuration, hidden submission, bulk-task
work, Finance grants, compensation fulfillment or a generic admin framework.

## Acceptance criteria

1. Preserve the closed public input structure, exact string quantities and
   optional empty definitions. Keep currency registration, binding eligibility,
   complete policy graph decisions and lifecycle authority in the backend.
2. Send POST drafts (201), PUT exact version (200), POST publication (200), or
   POST retirement (200). Preserve supplied UUID spellings in requests and
   compare returned UUID identity. Require an explicit idempotency key.
3. Validate all sixteen mutation-receipt fields: identities, operation key,
   requested project/policy/version, expected event, positive unbounded version
   integers, nullable prior-version pair, status transition and timestamp.
   Validate the digest's representation without inventing a client digest:
   backend canonicalization includes the authenticated actor. Immutable replay
   receipts describe the original event, not the aggregate's later status.
   Create validates server-issued policy/version UUIDs; the other operations
   bind both to the caller's selected path identities. Prior ID and number must
   be both null or both present with a positive number. First create is
   null→draft with no predecessor; successor create is active→active with a
   predecessor. Update keeps draft/active aggregate status and draft→draft;
   publication is draft/active→active and draft→published. Retirement is
   active→retired, published→retired, with predecessor equal to the selected
   version and number. The digest is `sha256:` plus 64 lowercase hex characters.
4. Emit the complete receipt in escaped text or JSON. Reject malformed,
   mismatched or credential-reflecting success as outcome unknown. Recover only
   by manually repeating unchanged selectors, body and key. Reads cannot prove
   rollback. Canonical denials remain distinct from ambiguous writes.
5. Process proofs cover all four wires, local input refusal, wrong-target/key
   receipts, nullable/history cases, exact quantities, large version integers,
   malformed responses and POST/PUT HTTP/2 replay refusal.
6. Extend the retained real public API/Flow/PostgreSQL guide-activation journey:
   use the CLI for unpaid draft/update/publication/retirement, compare REST and
   stored facts, prove exact replay and changed-input conflict, and deny
   PM-only/foreign/revoked/suspended callers without policy changes. Preserve
   current/historical reads, guide activation and locked-policy proofs. Native
   unpaid evidence does not certify compensated binding eligibility or payouts.
7. A receipt target-binding mutant must fail its intended process regression
   after a valid control. Required hosted completeness remains unchanged.

## Implementation decisions

The four commands reuse the existing Finance group, closed JSON parsing, UUID
identity checks, bounded transport, escaped output and caller-key machinery.
The first JSON PUT uncovered a shared POST/PATCH-only mutation classification;
PUT now receives the same non-rewindable body, uncertain-outcome and canonical
error handling. The HTTP/2 regression reproduces that defect before the fix.
Public input validation checks shape and preserves exact quantities; the owner
still decides economic validity and current authority. The retained native
activation journey now performs the Finance lifecycle through the built CLI and
compares immutable events with REST replay and PostgreSQL rows.

Plan review corrected explicit create-versus-selected-target binding and nullable
predecessor parity before implementation. Runtime/review results belong to the
PR evidence; this disposition records the intended merged capability.
Implementation review also made predecessor relationships explicit: draft
update/publication has no predecessor, active successor events have one, and a
non-retirement predecessor is a distinct earlier version. Retirement names the
selected version itself. Focused process counterexamples protect these rules.
