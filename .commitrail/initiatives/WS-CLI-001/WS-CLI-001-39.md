# WS-CLI-001-39 — Explicit administrative mutations in the CLI

- Initiative: `WS-CLI-001`
- Durable disposition: `Planned`
- Intended merge outcome: The existing public administrative actor, identity-link, and grant mutations are usable through one bounded Go CLI surface without moving authority or lifecycle ownership from Workstream.

## Intent

Issue #607 asks an Access Administrator to make explicit service-actor, actor-profile, identity-link, and administrative-grant decisions through the CLI. This matters because the API already owns those decisions, but the shipped CLI cannot invoke them. A successful privileged read must not be treated as authority for a later write.

## Current behavior

`backend/app/api/router.py` composes the authorization router under `/api/v1`; `backend/app/modules/authorization/router.py` exposes all eight requested POSTs with caller-supplied UUID `Idempotency-Key` and AUTH decisions. `catalogue.py` marks the actions active and `policy.py` assigns their permissions to Access Administrator. Real PostgreSQL guards, replay, lifecycle distinctions, final-administrator protection, and denial paths exist in `backend/tests/test_auth.py` and `backend/tests/authorization/admin_access/`. At current main `c6d916cc12a875ee76c45ae4130757654bc9152a`, #606 has already delivered one `admin` command root and its actor, identity-link, catalogue and grant-history reads. #607 must attach writes to that existing tree; successful reads never prove current write authority.

- Keep actor-profile suspension/reactivation/deactivation distinct from identity-link revoke/reactivate; neither silently performs the other. Do not alter #606 reads or their response validators.

## Design and decisions

Add explicit subcommands under #606's `admin` tree: `service-actor provision`; `actor suspend|reactivate|deactivate ACTOR_ID`; `identity-link revoke|reactivate LINK_ID`; and `role-grants issue|revoke [GRANT_ID]`. Require a bounded caller-authored JSON input file and UUID idempotency key for every write; transmit the exact body bytes, with local checks for the closed public shape, service identity/role/scope tokens and UUID selectors. Do not infer or fill target IDs or authority from a prior read. Issue/revoke grant remain administrative, not project Submitter/Reviewer grants. Preserve exact `201` versus `200` and validate complete privacy-bounded response shapes, selected resource UUID identity/type/version, and service-identity echo. Pass raw validated JSON to `--output json`; escape text. On transport loss or malformed success, report uncertain outcome with an action-specific unchanged-manual-replay instruction and never retry automatically. Canonical API 4xx denials remain denials.

Input validation must reflect three different public contracts, not a shared invented reason rule: `ServiceActorProvisionBody.reason` permits any nonempty 1–500 UTF-8-byte string without trimming; its `subject` is 1–200 UTF-8 bytes, non-NUL and without leading/trailing whitespace. `ActorLifecycleBody.reason` is trimmed by the server, then must be non-NUL and 1–500 UTF-8 bytes; preserve the submitted bytes on the wire and compare replay under the server's normalized reason semantics. `AdminRoleGrantIssueBody` and `AdminRoleGrantRevokeBody` reasons are nonempty 1–500 UTF-8 bytes, reject NUL, and are not trimmed. For a system grant, `scope_project_id` may be omitted or null; for a project grant it must be a UUID. Access Administrator and Operator are system-only. The backend remains the final validator.

Success validation follows the declared nullable shapes: profile and link lifecycle responses have `resource_type`, selected UUID `resource_id`, `http_status: 200`, and `version` absent or null (never numeric). Grant issue/revoke have `resource_type: admin_role_grant`, selected grant UUID on revoke, `version: 1`/`2` and `http_status: 201`/`200`. Service provisioning has an active profile/link, fixed provisioning method, requested service identity, UUID profile ID and valid timestamps; it has no authority grant or lifecycle `version` field. Reject unknown, malformed or identity-mismatched response facts without presenting the write as known to have failed.

Final-administrator proof must use a reachable public sequence. A self-revoke or self-suspend is denied by the earlier resource guard (`self_role_revoke_forbidden` or `resource_guard_denied`) and cannot prove the last-effective-administrator guard. With two effective administrators A and B, have A revoke B's grant; B's attempted cross-revoke of A's grant then fails fresh authorization and A remains effective. The existing serialized PostgreSQL test `backend/tests/authorization/admin_access/test_grant_concurrency_postgresql.py::test_cross_revoke_retains_one_effective_admin` proves this control-lock race and its exact `200`/`403 permission_not_granted` outcome. The CLI journey needs only a representative public cross-revoke/authority-loss path and retained-one-administrator assertion; it must not assert an unreachable `last_access_administrator` response. `backend/tests/test_authorization.py` directly exercises the defensive last-administrator conflict branches for profile suspension and link revocation; `AdminRoleGrantService.final_access_administrator_conflict` remains backend-owned. No CLI override or new backend guard is proposed.

Use one cohesive API/command pair for the three related administrative mutation families. If implementation or review reveals more than one independently reviewable authority boundary, split before code rather than diluting proof. Reject a duplicate `admin` root or a CLI-held authorization matrix; the backend is the sole authority. #606 is a sequencing dependency for coherent command discovery, not proof of write permission.

## Acceptance criteria

- [ ] Each of the eight exact public POSTs is reachable through one discoverable command and emits complete text/JSON, with explicit reason/body and key.
- [ ] Built-binary tests bind exact method/path/body/key/status and UUID-selected response, reject malformed, mismatched, reflected or control-bearing replies, and send no request for invalid local inputs. They preserve the three reason contracts, subject constraint, grant scope omission/null, and lifecycle `version` omission/null without inventing stricter rules.
- [ ] Lost/malformed write replies are uncertain; API-authored 4xx denial, idempotent same-key replay and mismatch are differentiated. No automatic retry, authority preflight, self-grant helper or final-admin override.
- [ ] Real signed API/PostgreSQL journey has bootstrap fixture only; the CLI performs all eight tested writes. It demonstrates service provision, profile transitions, link transitions, grant issue/revoke, exact same-key replay, and denied non-admin, revoked and suspended callers. A reachable two-administrator cross-revoke/authority-loss sequence leaves one effective administrator; backend conflict tests retain direct guard proof. Tests must distinguish profile from link effects and show grant revocation is not reversed by link reactivation.
- [ ] Existing #606 reads and delivered commands remain available without duplicate registration; docs distinguish implemented CLI exposure from deployment and preserve backend authority.
