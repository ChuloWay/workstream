# WS-CLI-001-35 — Repair exact blocked task revision context

- Initiative: `WS-CLI-001`
- Durable disposition: `Planned`
- Intended merge outcome: A Project Manager can explicitly repair one current revision context through the existing public API using an exact parent or missing-root routing source.

## Intent

The backend already owns atomic, authorized revision-context repair, but the CLI has no way to invoke it. Expose one deliberate manager command so a human or agent can supply the exact source, explanation, and caller-owned replay key. Keep the backend authoritative for current manager permission, task/assignment/routing lineage, clock, eligibility, audit, and replay.

## Current behavior

`backend/app/modules/tasks/router.py` publishes `POST /api/v1/projects/{project_id}/tasks/{task_id}/revision-context/repair`. `TaskRevisionRepairRequest` accepts exactly one parent preparation ID/digest pair or missing-root routing manifest ID, plus a reason. The operation returns `ContributorRevisionContext` with a running or paused clock and current disposition. The CLI's `project task PROJECT_ID TASK_ID` already reads manager task detail including its revision context; `cli/internal/api/revision_context.go` validates that shared projection. No CLI repair command exists.

## Bounded change

### Allowed

- Add `cli/internal/api/revision_repair.go` for the one public POST and reuse `validateRevisionContext`.
- Add `cli/internal/command/revision_repair.go` and register it under the existing `project task` in `cli/internal/command/tasks.go`.
- Add focused built-binary HTTP tests and one real API/PostgreSQL CLI journey under `cli/tests/integration/`.
- Update `cli/README.md`, affected `docs/roadmap_status.md` claims, and this record. The initiative overview and index are coordinated by the CLI lead.

### Not allowed

- No backend route, schema, owner, authentication, authorization, policy, or migration changes; no edits to `cli/internal/api/client.go`, dependencies, CI, or release packaging.
- No second context read, human-review command, automatic repair/rebase, deadline reset, local permission or policy decision, automatic retry, fallback selector, or compatibility path.

## Design and decisions

`workstream project task repair-revision PROJECT_ID TASK_ID --idempotency-key UUID --reason TEXT` requires either `--parent-preparation-id UUID --parent-preparation-sha256 sha256:<64 lowercase hex>` or `--routing-manifest-id UUID`. The API method validates only closed input shape and safe transport, sends one keyed POST, validates the actual response schema, preserves raw authorized JSON, and presents escaped text. The response has no project/task/key echo, so no invented binding field is assumed. Unknown write outcomes remain unknown; a caller may deliberately replay only the unchanged exact request and key. The manager detail read remains an observation, never write authority.

Rejected: an automatic read-and-repair sequence, client-side eligibility inference, and a duplicate manager revision read.

## Acceptance criteria

- [ ] One command sends the exact public path, bearer, key and exclusive JSON body once; malformed input fails before HTTP.
- [ ] Both response clock shapes and blocked/ready disposition survive JSON and escaped text. Malformed or substituted successes are unknown outcomes, not success.
- [ ] Canonical denial, exact replay, mismatched replay, foreign project/grant, revoked authority and changed lineage remain backend-controlled through real API/PostgreSQL proof where fixture-reachable.
- [ ] Existing `project task PROJECT_ID TASK_ID` read and other commands remain unchanged; no backend or CI change.

## Risk and review routing

- Risk class: `L1` — a bounded, authenticated lifecycle write.
- Required reviewers: security, QA and test delta; architecture, reuse and documentation for the actual diff.
- Human review focus: exact source/key identity, authoritative backend authorization, honest unknown-outcome reporting, and no implied deadline reset or automatic repair.
