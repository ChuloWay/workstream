# WS-CLI-001-38 — Explicit guide sufficiency report and warning acknowledgement

- Initiative: `WS-CLI-001`
- Durable disposition: `Complete`
- Intended merge outcome: A Project Manager can submit a manual guide sufficiency report and explicitly acknowledge its warnings through the existing public API from the CLI, with exact replay and no inferred setup readiness.

## Intent

Issue #601 asks the CLI to expose four existing project-guide writes. This first bounded change covers the two sufficiency writes; a later separately reviewed change covers manual artifact-policy create/update. The split follows distinct backend owners and preconditions: a human-authored report or acknowledgement is not the authoritative compiled setup report required to create a policy. Keeping these actions separate prevents a CLI workflow from presenting acknowledgement as compilation approval or policy activation.

## Current behavior

`backend/app/modules/projects/router.py` publishes `POST /api/v1/projects/{project_id}/guides/{guide_id}/sufficiency-reports` (201) and `POST /api/v1/projects/{project_id}/guides/{guide_id}/sufficiency-reports/{report_id}/acknowledge-warnings` (200). Both use `sufficiency_authorization`; their actions are active in `backend/app/modules/authorization/catalogue.py`, unlike planned-only ART Operator actions. `GuideSufficiencyMutationService` owns exact draft-guide/latest-snapshot lineage, Project Manager PREP consumption, one-report-per-snapshot creation, warnings-only acknowledgement, replay and conflict behavior. `backend/tests/test_projects.py` proves manual create/replay and shows that a compiled report whose setup run already emitted policy cannot use this acknowledgement route. A successful normal compilation projects an authoritative report and unified policy together; manual policy POST can create a separate draft afterward, but the removed manual approval route means that draft cannot control guide activation. The bounded public API/PostgreSQL probe now reaches manual policy POST/PATCH after owner-produced setup, but the later policy CLI commands remain unimplemented. The pending #600 CLI branch adds `project guide sufficiency list/show` and a closed `validateSufficiency` response validator; it is not merged at this base and must be reconciled, not copied or stacked as an unreviewed dependency.

## Design and decisions

Send the caller's bounded, schema-shaped JSON unchanged with the required `Idempotency-Key`; validate only public schema/identity/size constraints locally and leave status/finding semantic decisions to the backend. Use the existing keyed request path with the larger bounded guide-inspection response limit: 100 findings can exceed the generic 64 KiB JSON limit. A successful response is retained diagnostic evidence, not a guide compilation, policy approval or activation. Validate response project/guide/report identity, manual-create provenance and required metadata against the selected route; a malformed write response is an uncertain outcome, never grounds for automatic retry. On transport uncertainty, instruct manual replay of identical selectors, input bytes and key. The two policy writes require authoritative setup report, manual-only draft lineage and a CAS hash. They remain outside this slice. Owner-produced setup followed by real public POST/PATCH has now proved bounded route reachability; separate CLI implementation and review remain.
