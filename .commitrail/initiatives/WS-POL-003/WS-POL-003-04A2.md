# WS-POL-003-04A2 — Hidden setup finalization

- Initiative: `WS-POL-003`
- Durable disposition: Complete
- Intended merge outcome: Implement hidden, immutable setup finalization after complete POL-04A3
  and make AUTH-12B2 the next usable boundary.

## Intent

Add the hidden, purpose-specific product boundary that atomically binds one
accepted unified compilation and its exact deterministic projections to the
current `ProjectSetupRun`. The boundary records immutable finalization custody
and moves the setup ledger to exactly one closed outcome. It remains unreachable
from HTTP and Celery until AUTH-12B2 and POL-04B merge.

## Required outcome

For one exact current setup generation, compilation and both required
projections are already persisted prerequisites. The finalizer only reads their
custody; it never calls a projection method:


```text
accepted ProjectGuideCompilation
-> exact guide-sufficiency projection operation
-> exact submission-artifact-policy projection operation when sufficiency passes
-> fresh setup-finalization authorization
-> immutable finalization receipt + one setup-ledger transition
```

| Compilation result | Required projections | Setup outcome |
|---|---|---|
| `guide_blocked` | Exact sufficiency report only; artifact-policy projection must not exist | `sufficiency_blocked` |
| `draft_ready` | Exact sufficiency report and exact artifact-policy draft | `policy_draft_ready` |
| `draft_ready_with_warnings` | Exact sufficiency report and exact artifact-policy draft | `policy_draft_ready` |

`current_step` remains diagnostic: it becomes `guide_sufficiency` for
`sufficiency_blocked` and `submission_artifact_policy_derivation` for
`policy_draft_ready`. It is not another lifecycle-status field.

Invalid, unsafe, provider-uncertain, stale, replaced, partial, mixed-generation,
or unprojectable results cannot finalize. Finalization is not Project Manager
approval, policy publication, guide activation, post-submit projection, or task
readiness.

## Product-owned immutable custody

Add one `ProjectGuideSetupFinalization` row for one exact setup generation.
Using the URL namespace and canonical seed
`<setup-run-id>:<setup-generation>:<compilation-id>`, derive separate UUIDv5
values with these exact names:

```text
finalization_id = workstream.project-guide-setup-finalization:receipt:<seed>
operation_id    = workstream.project-guide-setup-finalization:operation:<seed>
correlation_id  = workstream.project-guide-setup-finalization:correlation:<seed>
```

Python's dependency-free public contract is the sole UUIDv5 derivation owner.
`test_finalization_identity_uses_exact_uuid5_namespaces_and_seed` fixes the exact
vectors. PostgreSQL enforces uniqueness and complete facts/authority/audit
agreement; it does not rederive UUIDv5 and needs no new extension.

The row contains:

- `id`, `operation_id`, and `correlation_id`;
- project, guide/version, source snapshot ID/hash, setup run/generation, and
  Celery task ID;
- compilation attempt/request/provider identities, compilation ID, canonical
  input hash, result hash/schema, agent name/version, and component hashes;
- sufficiency operation ID, report ID, and output digest;
- nullable artifact-policy operation ID, policy ID, and output digest;
- result classification and closed setup outcome;
- finalization facts digest, authorization decision event ID, and authority
  resource digest;
- authorized actor profile, identity link, fixed service identity, action,
  permission, scope, and database-owned `created_at = transaction_timestamp()`.

The artifact-policy triple is all-null only for `guide_blocked`; otherwise all
three values are required. Composite foreign keys bind the receipt to the exact
compilation, setup generation, and projection rows. There is exactly one receipt
per setup generation, compilation, operation, and authorization decision.

The receipt is append-only. PostgreSQL unconditionally assigns
`NEW.created_at := transaction_timestamp()` on insert, so ORM or direct-SQL
writers cannot supply or preserve a forged receipt time. PostgreSQL rejects
update, delete, and truncate and rejects any receipt whose classification,
projection shape, output IDs, or lineage disagree with the referenced
immutable rows.

## Setup-row transition

The source setup row must still have the exact 04A3 projection source shape:

- latest setup generation and source snapshot for the locked draft guide;
- `status = queued`, `current_step = queued`, exact deterministic Celery task ID;
- no error, start, finish, post-submit summary, or setup output IDs;
- an internally consistent optional ART continuation pair; and
- no existing finalization receipt.

Finalization changes only:

- `output_sufficiency_report_id` to the exact receipt report;
- `output_submission_artifact_policy_id` to the receipt policy or `NULL`;
- `status` to the closed setup outcome and `current_step` to its exact
  diagnostic value defined above; and
- `finished_at` to PostgreSQL-owned `transaction_timestamp()`.

Every other setup field remains unchanged, including `updated_at`. Use an exact
Core update explicitly supplying the locked `updated_at` so SQLAlchemy's
`onupdate=func.now()` cannot widen the transition. Both service before/after
and direct-SQL mutation-width proof include that column. A transaction-deferred database
constraint guard requires the setup transition and matching receipt in the same
transaction in both directions. It permits the service's receipt-then-transition
statement order but rejects commit when either side is orphaned. It also rejects
partial output assignment, cross-resource output IDs, later mutation of a
finalized setup, and deletion/truncation of custody. The independently enforced
receipt and setup timestamp triggers establish their shared transaction clock;
the deferred custody guard does not claim a separately injectable clock state.

The setup guard applies to generations owned by a unified compilation,
projection operation, or finalization receipt, including the interval before a
receipt exists. Legacy-only generations retain their current worker behavior.
Once a receipt exists, its setup row is immutable. Unified `policy_draft_ready`
rows therefore cannot enter the legacy same-row post-submit continuation.
Before POL-04B exposes this path, its cutover must account for this boundary;
POL-05/06 or an earlier reviewed migration owns separate downstream custody.
This chunk adds no downstream transition permission.

The finalization transition never accepts application-owned time. Its database
trigger unconditionally assigns `NEW.finished_at := transaction_timestamp()`
after validating the transition, so a direct writer cannot forge, preserve, or
advance the completion time. The immutable receipt's database-owned creation
time and the setup completion time therefore share the same transaction clock.

## Public authorization port

The public PROJECTS command `ProjectGuideSetupFinalizationCommand` contains
exactly `project_id`, `guide_id`, `setup_run_id`, `setup_generation`, and
`compilation_id`, with parsed UUIDs and a strictly positive integer generation.
No caller supplies operation IDs, facts, times, or authorization state.
`GuideCompilationFinalizationService(session, authorization=None).finalize(command)`
requires an active, non-nested caller-owned root transaction and never commits.
Missing, stale, or foreign selectors use concealed `source_state_unavailable`;
authority failure uses `service_authority_denied`; database failure uses
`storage_unavailable`. Callers roll back the root transaction on every failure.

AUTH's dependency-free public API declares `ProjectSetupFinalizationLocator`
with only `project_id` and `operation_id`, `ProjectSetupFinalizationFacts` with
the exact canonical keys below, nominal `PreparedSetupFinalization`, and
`SetupFinalizationAuthorizationPort`. `ProjectSetupFinalizationAuthorityReceipt`
contains exactly `decision_event_id`, `actor_profile_id`, `identity_link_id`,
`service_identity`, `action_id`, `permission_id`, `scope_project_id`,
`resource_type`, `resource_id`, and `resource_context_digest`. PROJECTS validates
every field against locked facts and fixed authority, recomputing the digest
before any product mutation. The persisted scope is project scope.

The async context-managed port exposes exactly:

```text
async with authorization.prepare_setup_finalization(locator) as capability:
    capability.consume_new(final_facts) -> authority_receipt
    capability.validate_replay(final_facts, stored_decision_id) -> None
```

The product service defaults to unavailable. AUTH-12B2 later provides the only
production adapter and activates only `project.setup_run.update` for fixed
service `workstream.project.setup` with permission `project.guide.manage`. This
chunk adds no catalogue row, evaluator, grant, service membership, or active
composition.

The locator contains only the non-locking project and operation locator needed
for AUTH preflight. PROJECTS then locks and recomposes every final fact. The
capability is nominal, process-local, non-serializable, single-use,
session-bound, root-transaction-bound, and closed exactly once in `finally`.

```text
root transaction
-> deterministic operation/facts identity
-> non-locking locator lookup
-> AUTH prepare
-> lock attempt and request, then guide, latest snapshot and latest setup
-> lock compilation and projections (matching existing projection lock order)
-> recheck the finalization operation and setup-generation receipt under lock
-> if an exact receipt appeared while waiting, validate replay and return it
-> validate exact source state and closed outcome
-> consume PREP with final facts
-> close PREP in finally
-> add immutable receipt
-> transition setup row
-> flush
-> caller-owned commit
```

Consume or close denial/exception occurs before product mutation. Any later
database failure rolls back the receipt, setup transition, and staged AUTH
evidence together.

## Replay, concurrency, and recovery

Exact replay locks the immutable receipt, uses the receipt's stored
pre-finalization `source_state_digest` to reconstruct the original final facts,
and separately proves that the current setup row exactly matches the receipt's
post-finalization status, diagnostic step, output IDs, and `finished_at`
value, including exact equality with the receipt's database-owned `created_at`.
It performs fresh current-service preflight, validates the stored decision, and
returns the same result without PREP consumption, new AUTH evidence, or
mutation. It must not recompute the pre-finalization source digest from the
already-mutated setup row. The finalizer recognizes replay through the finalization operation and never
invokes either 04A3 projection method. POL-04B's future live coordinator owns
checking finalization before projection calls on reentry; its acceptance must
include `test_finalized_setup_replay_short_circuits_before_projection_methods`
with a discriminating ordering defect. An unused poisoned projection fake in
04A2 is not evidence for that future coordinator.

The initial non-locking lookup is only a preflight optimization. Every new-path
caller must re-query both the deterministic operation identity and the unique
setup-generation receipt after acquiring the setup serialization lock and
before source-state validation or PREP consumption. An exact receipt that
committed while the caller waited switches that same prepared capability to
`validate_replay`; the capability then closes exactly once and returns the
stored result without new authorization evidence or product mutation. A
same-operation facts mismatch or a different operation already owning the
generation denies without PREP consumption. This post-lock recovery check is
mandatory and cannot be inferred only from a uniqueness violation.

Concurrent identical calls produce one receipt and one setup effect; the loser
returns the same valid result. Same-operation different facts,
different-operation attempts on one generation, stale compilation/projection
lineage, replaced guide/snapshot/setup generation, and cross-resource requests
fail closed without another effect.
