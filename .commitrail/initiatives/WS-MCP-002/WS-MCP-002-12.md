# WS-MCP-002-12 - Task execution and submissions

- Initiative: `WS-MCP-002`
- Durable disposition: `Complete`
- Intended merge outcome: Expand the independent MCP adapter from 90 to 108
  tools with the current public task execution, preparation and submission APIs.

## Intent

Let authorized contributors and project managers execute the supported task and
submission workflows through fixed MCP tools. The adapter forwards the caller
bearer unchanged. Workstream remains the only identity, authorization,
idempotency, lifecycle and submission authority.

## Bounded change

### Allowed

- `mcp_server/`: eighteen selected public contracts, one task-execution tool
  module, fixed gateway/schema/registry bindings, focused tests and package docs.
- `.github/workflows/mcp.yml`: exact 108-tool container and contract assertions.
- This record, the initiative overview/index and affected capability status.

### Not allowed

- No backend, CLI, database, authorization or identity behavior changes.
- No generic HTTP tool, private backend import, direct database access, local
  authorization/lifecycle/replay state, generated mutation key or automatic retry.
- No task-management override, import, audit, service-actor or health tools.

## Design and decisions

The change adds three preparation operations, eight contributor task operations,
three contributor submission operations and four manager task/submission reads.
Each tool owns one fixed method/path/status tuple captured from current backend
OpenAPI. Callers cannot provide a URL, HTTP method or bearer as tool input.

Preparation accepts one bounded Base64 ZIP plus typed assignment, idempotency and
optional submission/revision header fields. The adapter decodes it once and sends
raw `application/zip` bytes. It stores no packet or replay state. Assigned guide
documents reuse the bounded binary-read projection: media type, Base64 bytes,
server-observed byte count and SHA-256. Ordinary JSON keeps its separate 64 KiB
response bound.

Screen, release, claim and start require caller-provided UUID idempotency keys.
Claim dispatches only claim; it never starts the task. Submission creation uses
the backend's ready admission and assignment identifiers and is deliberately
unkeyed because the current public contract is unkeyed. Workstream performs every
fresh authority, state, preparation, checker and admission decision.

Successful reads bind returned task, project, preparation or submission selectors
where the public response exposes them. Successful mutations bind available
authoritative selectors. A malformed or substituted read fails as an invalid API
response; a malformed mutation result is uncertain execution. The adapter never
retries a mutation automatically.

## Acceptance criteria

- [x] Exactly 108 unique tools and zero resources/prompts.
- [x] Eighteen selected OpenAPI snapshots are tamper-evident and drift-tested.
- [x] Every fixed method/path/status binding matches its reviewed snapshot.
- [x] Invalid input and substituted success responses fail closed before reuse.
- [x] Preparation and guide-document bytes are bounded and never logged.
- [x] Caller bearer and mutation keys are forwarded unchanged and never generated.
- [x] Claim never dispatches start; no mutation is retried automatically.
- [x] No local authorization, replay state, database access or private backend import.

## Risk and review routing

- Risk class: `L1`
- Required reviewers: security/authorization, architecture/reuse, QA/test delta,
  documentation and CI integrity.
- Human review focus: fixed routes and headers, binary bounds, claim/start
  separation, submission-admission binding, uncertain execution and token privacy.
